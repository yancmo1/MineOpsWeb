# Catalog validation

Every ingestion payload produces an immutable staged snapshot keyed by its source hash. Snapshot activation is explicit. Validation covers artifact schemas and release identity, duplicate/orphan identifiers, relationship integrity, deterministic serialization, artifact hashes/byte counts, unresolved-evidence count parity, and suspicious changes. `manager-domain.json` is required whenever it is listed because exact manager tables must not silently disappear while the package remains usable. Client-runtime `required` flags do not weaken review integrity: every manifest-listed artifact must exist and match its hash, byte count, and supported schema version or the package is quarantined. Captured Unity object records must include complete base64 bytes, byte length, and SHA-256, or a linked entry in `unresolved-evidence.json`; the package builder verifies the byte metadata and the review layer verifies those links. Equipment source records follow the same complete-byte contract. The review layer also quarantines identity, duplicate-ID, optional-manager-domain, and unresolved-count mismatches; unresolved semantics can remain review warnings when their raw evidence is retained.

Release identity is the immutable `releaseId + manifestSha256 + validationReportSha256` tuple. Oracle stores each package under `/pb/catalog-artifacts/releases/<releaseId>/`; review recomputes both hashes from those server-mounted files and refuses submitted/stored mismatches. Publication requires one unique release row, one latest approved review bound to both hashes, and one publication pointer. Publish and rollback update release statuses, pointer metadata, audit logs, and a timestamped publication event in one transaction. Direct collection writes are closed, release IDs are unique, and a partial unique index enforces one latest review per release. Historical ambiguous rows are retained under `legacy-...` identities rather than deleted or rebound.

Never mutate an active snapshot to correct it—generate, validate, review, and publish a replacement with a new release ID. A catalog-only recovery uses the authenticated rollback route; restoring the verified PocketBase backup is reserved for control-plane/schema recovery.

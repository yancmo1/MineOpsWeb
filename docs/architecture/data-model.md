# Data model

Player data remains revisioned and user-scoped: `users`, `player_managers`, `mutation_log`, and snapshot/history records use stable UUIDs with `created_at`, `updated_at`, `deleted_at`, `revision`, and `device_id`. `player_managers` preserves the iOS active fields: manager key, unlock state, level, rank, promotion, and fragments.

The web client also records fragment provenance on the local player row when a Kolibri save supplies a fragment count, when it was manually retained, or when the current save shape omits it. An omitted count is displayed as unavailable and never treated as a real zero. Player-specific passive values are likewise retained only when present in the Kolibri manager row, in source order; the detail UI renders a red missing marker when an unlocked passive has no imported value. Equipment assignment IDs come from Kolibri, while effect text/multipliers come only from explicit verified catalog fields; neither assignment nor effect is inferred. Resource and owned-equipment rows discovered under resource-shaped Kolibri sections are stored separately in the local `inventory` table with their original save path/key and remain unresolved until the field semantics are verified.

Static game data is not modeled as one PocketBase record per object. It lives in immutable, versioned JSON release packages with a manifest and separate artifacts for catalog core, relationships, mappings/evidence, localization, assets, validation, and changelog data. APK strategy packages also carry `manager-domain.json`, `equipment-domain.json`, `passive-domain.json`, `strategy-configs.json`, and `unresolved-evidence.json`, plus the conservative semantic-lift artifacts `research-domain.json` (skill-node identities with region/continent), `mine-economy-domain.json` (continent identity map), `frontier-domain.json` (event/season/battle-pass configs), and `power-score-domain.json` (settings evidence with an opaque Q16 payload — field names unverified). `passive-domain.json` joins passive IDs to manager unlock milestones and rank effects and explicitly reports when the APK has no value table for rarity/rank/promotion calculation. Canonical IDs and source identifiers remain in JSON, including unresolved objects; unverified config meaning stays raw and explicitly unresolved instead of being promoted into a gameplay claim.

Manager passive identity is release-scoped catalog data (`passiveId`, type, value, and unlock requirement); passive availability is player-scoped and derived from imported promotion/level. Identity-only APK rows may be enriched for presentation, but stable APK passive IDs take precedence over legacy row-position labels. A passive with no verified requirement remains unavailable to scoring rather than failing open. Exact manager level, promotion, rank, fragment, and effect tables are preserved with per-object bundle/path provenance rather than flattened to one representative parameter. The strategy and detail adapters prefer exact active-level rows, apply the matching APK rank active-effect factor when available, and keep the older catalog interpolation only as a compatibility fallback.

PocketBase stores only control-plane records: release metadata, raw-import provenance, artifact manifests/references, validation summaries, lifecycle/review state, audited manual mapping overrides, publication pointers, and audit history. A player snapshot records the catalog release ID and manifest hash used to interpret it so newer catalogs can be applied as a new interpretation without destructive player-data migration.
